# 本地参考图片观察与采用建议

查看日期：2026-11-06。观察对象为用户提供的三张静态截图，已逐张直接查看原图。

本记录中的“观察事实”仅指截图可见内容，不能证明原产品的交互行为、控件可用性或模型能力。截图的原始网站与拍摄时间未核实。下列采用项为当前线框设计建议，最终以 FigCraft 工作稿及交付说明为准。

## 1. `image.png`：用户入口展开菜单

- 本地文件：`我觉得可能用得上的参考图片/image.png`。
- 观察事实：底部用户行上方显示展开面板。面板顶部同排展示头像、用户名、账号标签和积分数值；其下有升级入口与活动卡片。菜单分组以细分隔线隔开，部分行显示当前值与右箭头，例如语言“简体中文”、主题“跟随系统”。底部是退出登录入口。
- 推荐借鉴：用户入口锚定侧栏底部；展开后先展示账号与积分，再排列主题、设置等操作。主题行显示当前选择，帮助用户理解此项可以更改；积分与充值入口保持相邻。
- 本项目映射：保留“账号信息／积分余额与充值／主题／设置”的层级即可。首张主画面可以只显示侧栏中的用户入口与余额；展开菜单在后续状态稿中表达。
- 不建议直接采用：升级会员、签到、邀请、消息、宠物、语言等内容不是本项目已确认需求；无需带入。同样不采用头像颜色、促销标签等视觉风格。
- 验证限制：无法从截图确认菜单触发方式、主题子菜单内容、点击后的页面或实际充值行为。

## 2. `image2.png`：含已上传附件的输入区

- 本地文件：`我觉得可能用得上的参考图片/image2.png`。
- 观察事实：输入容器内部上方有一张附件卡片，包含缩略图、文件名、PNG 格式及 1.2 MB 大小。文本编辑位置在附件下方。底部工具行左侧为添加和其他控件，右侧包含选择器、音频相关图标及发送按钮。输入容器外还有一条辅助工具栏。
- 推荐借鉴：将“附件区域—文本区域—参数与发送工具栏”分成明确的三层，但放在同一输入容器中，表达它们共同属于待发送消息。附件卡片同时提供缩略图和文件名，便于核对上传对象；发送操作固定在工具栏右端。
- 本项目映射：附件区域用可编辑的重复附件项组织，多张时仍保持同一行或明确的可滚动条带。发送按钮与预计积分相邻。模型、档位及生成参数放入底部工具栏，避免夹入提示词文本。
- 设计建议（不是截图事实）：为每张附件增加明确的移除入口；在附件区域标明数量。截图没有展示移除按钮、多附件、上传中或上传失败，不能据此宣称这些行为已验证。
- 不建议直接采用：自动审批、环境／项目选择、语音及应用连接图标不属于本项目需求。线框使用中性色，不沿用绿色发送按钮。
- 验证限制：无法确认附件卡片可否打开预览、文件名如何截断、上传限制、拖放行为或容器随附件增加的实际变化。

## 3. `SnowShot_2026-11-06_14-58-39.png`：图像生成输入与参数排列

- 本地文件：`我觉得可能用得上的参考图片/SnowShot_2026-11-06_14-58-39.png`。
- 观察事实：画面标题为“Board”；宽输入框上方区域显示“Describe your image”。底部左侧依次出现加号、“Auto”下拉、比例“1:1”和“1× / 2× / 4×”分段控件，当前“1×”以实底强调；发送图标位于输入框右侧。输入框下方另有“All”下拉与“Upload designs”按钮。
- 推荐借鉴：提示词区域与参数行分层；参数采用紧凑控件并展示当前值。短且固定的一组离散选项可用分段控件表达单选，其他较长选项用下拉。添加入口与生成参数归于同一输入容器。
- 本项目映射：借鉴参数排列与选中状态表达；“模型—条件档位—比例—清晰度—数量”根据已验证的参数规则组织。1440 × 900 画面内优先保证工具栏可读，不要求将所有选择项都展开。
- 推测边界：“1× / 2× / 4×”可能表示生成数量，但截图未标明语义；不得把它作为数量规则证据。也无法仅凭“Auto”确定它一定代表模型。
- 不建议直接采用：Board 页面整体结构、外置的“All”与“Upload designs”不直接复制到对话式创作页；是否需要图库上传功能尚未确认。
- 验证限制：无法确认菜单展开内容、数量上限、按钮是否可用、发送后的结果形态或上传后的布局。

## 对首张代表性画面的组合建议

首张画面优先采用第二张图的“附件／文本／工具栏”输入区层级，以及第三张图的紧凑参数控件与当前值表达。侧栏底部用户入口采用第一张图的账号和积分归组方式。三者只影响布局与组件关系，不确定最终视觉风格，不新增未确认的业务功能。

如要在首张画面同时表达已完成结果和下一轮上传，建议将“上一轮用户消息及结果”放入中央对话区，将“下一轮参考附件及提示词”留在底部输入区，并在设计标注中解释归属。不要将待发送附件误放进上一轮结果组。
