# 网站图片缩略图与预览

本文记录网站显示图片的当前实现及后续改进建议；不涉及设计验收截图，也不改变原图下载、附件生成输入或业务数据。接口见 [接口契约](api-contract.md)，加载配置见 [部署说明](../deploy/README.md)。

## 已实现

| 场景 | 当前资源与行为 |
| --- | --- |
| 生成结果列表 | 使用长边不超过640px的WebP缩略图，质量82；当前前端还将1600px预览作为2x候选 |
| 图库卡片 | 使用640px缩略图；目前没有按卡片尺寸或DPR提供更多候选 |
| 生成结果大图弹窗 | 使用长边不超过1600px的WebP预览，质量93；下载保留原图 |
| 对话框62px附件小图、悬停预览、历史附件 | 当前都使用附件原图；站内生成图加入附件后，也未使用其已有的缩略图和预览URL |

生成图衍生处理见 [thumbnail.go](../internal/studio/thumbnail.go)：等比缩放、不放大小图，应用EXIF方向并保留透明通道；首次访问生成并持久缓存，历史图按需生成。当前编码器虽能输出WebP，入口检查只接受PNG/JPEG，不能直接用于全部上传格式。

图片响应先认证并校验归属，包括缓存命中和304。浏览器使用私有缓存、Cookie隔离及ETag重新验证；当前304之前仍读取图片BLOB并计算哈希。附件小图和悬停共用URL，通常能复用浏览器资源，不能据此断言每次悬停都会重复下载；问题是小图首次加载就可能传输整张原图。

## 尚未补齐

- 上传附件支持PNG/JPEG/WebP/GIF，但 [附件接口](../internal/studio/studio_attachments.go) 只有原图URL，没有独立衍生图路由与缓存。旧输入预览不能等同于当前六附件链路已接入。
- [附件组件](../frontend/src/features/create/DialogAttachments.tsx) 只读取原图URL；生成图已有的衍生字段没有用于小图和悬停。
- 生成结果将640/1600档简单标作1x/2x，图库没有候选选图，尚未统一按实际显示尺寸、纵横比和设备DPR选择资源。
- 缺少完整的衍生图加载失败回退；字段缺失时的URL回退不等于网络或解码失败时能回退。
- 当前质量值没有照片、文字截图、透明图的对比评估，不能宣称最优；尚无明确的动画预览、ICC色彩管理或“衍生图比原图大”的处理策略。

## 建议实施顺序（待实施）

1. **先补附件链路。** 站内图优先复用已有衍生URL；上传附件新增固定版本衍生路由、缓存及可选URL字段，并同步历史附件。原图URL继续用于下载和生成输入。历史图片访问时懒生成，不批量重编码。
2. **按用途选图。** 62px小图评估新增256px档；悬停复用现有640档，大图弹窗复用1600档。当前悬停图片区最高316×288px，640档通常覆盖DPR2，更高DPR按实际尺寸选择更大档。小图使用cover填满时，极端纵横比应沿用当前裁切生成方形小图，或按裁切后的像素需求选档，不能只看源图长边。
3. **统一格式和错误处理。** 对四种上传格式做受像素/字节限制的安全解码；GIF建议生成静态预览，保留原件，实施前确认其动画展示语义。为可用衍生图提供有次数限制的原图回退；认证失败沿用登录处理，不循环重试。
4. **再优化质量与缓存。** 用合成照片、文字截图、透明图和极端比例样本比较清晰度、体积、编码耗时与内存，再确定质量、无损分流及小文件策略。缓存ETag、MIME和长度等元数据，鉴权后先判断304，再读取BLOB。当前优先级高于引入AVIF或额外编码依赖。

256px是新增候选，640/1600px是现有档位的复用建议，并非所有组件的固定规范。选图覆盖不同浏览器缩放和DPR；若使用srcset宽度描述符，必须标注衍生图真实像素宽度，不能把长边档位直接当作宽度。限制为固定用途和版本，避免任意宽度/质量参数造成缓存无限增长。

## 审查证据与后续验证

2026-11-10用当前生产前端构建和本地合成API数据核对DPR1/2的真实浏览器请求：生成结果分别选择缩略图/高清预览；上传附件和站内图附件的小图、悬停均选择原图URL，两组无浏览器错误。该验证只证明资源选择，没有读取生产图片或测量真实生产节省比例。

后续实现按 [测试矩阵](../tests/README.md) 验证四种格式、透明/方向/极端比例、小图不放大、历史图首次访问、权限与304、失败回退，以及不同缩放/DPR下的实际请求和画质；使用本地合成样本，不调用收费生图接口。
