# 固定工作目录与发布流程

## 聊天归档后继续工作

GitHub仓库与聊天相互独立。会被清理的是聊天的Codex托管工作树，而不是远程origin或已推送的提交。[官方工作树说明](https://developers.openai.com/codex/app/worktrees/) 说明归档关联聊天会触发托管工作树删除，删除前保存快照，重开聊天可恢复。

推荐日常使用普通独立Git检出 `D:\workspace\img-gen-current`，在Codex中将它打开为项目，并使用Local模式开新聊天。它不是Git worktree，也不位于 `.codex/worktrees`；更换或归档聊天后，新聊天仍打开此固定项目。

旧 `D:\workspace\img-gen` 的main与远程存在分叉，并有未提交的 `.env.example` 删除，不能用reset或盲目pull整理。新固定检出保留当前代码和GitHub origin，旧目录原样保留。环境配置不会从旧项目或服务器自动复制；需要本地运行时再按实际配置。原UI Studio是另一套模拟设计源码，不能当作已接入服务端的生产工作目录。

固定目录内的未推送提交依然需要自行备份；独立检出保证不随托管聊天工作树清理，不等于自动同步GitHub。当前设置明确不自动推送。项目在Codex中的路径需切换到此固定目录；仅在磁盘创建目录不会自动修改现有项目的路径。

## 减少重复工作

运行 `node scripts/prepare-release.mjs` 只做本地准备：

1. 要求工作区干净，明确源码提交。
2. 依赖锁文件、Node/npm版本未变化且安装记录完整时跳过npm ci。
3. 前端源码、配置、工具版本和上次产物校验和一致时复用前端构建。
4. 同一Git提交、Go版本、前端产物和二进制校验和一致时复用Linux amd64二进制。
5. 写入 `outputs/releases/<提交号>/release.json`，列出源码、静态文件与二进制SHA256。缓存放在 `.local/release-cache/`。这些目录均不提交。

缓存记录、源码或产物变化会使相应构建重新执行；依赖首次准备会安装一次。Go使用已有工具链缓存，前端仅构建一次。该脚本不执行git push、不调用ssh/scp、不修改线上环境、不自动跑业务测试。测试仍按实际改动执行一次，现有CI继续提供完整检查。

发布确认后复用这份产物，使用现有OpenSSH/scp流程即可。一次上传完成后执行一次服务端发布操作；保留队列检查、数据库/配置备份、SHA256校验、原子切换、失败回滚及健康检查。当前备份是较大的历史数据快照，不能为了提速取消。进一步缩短停机时间需要单独设计在线备份或数据库连续恢复策略，不在本轮修改。

纯文档修改通常不需要重新发布网站。UI小改只检查相关交互；用户明确人工验收时，部署后检查服务健康和页面资源即可。

## MCP与插件的选择

当前已有Git、Node、Go和OpenSSH，增加GitHub或SSH MCP并不会自动加速构建或数据库备份。优先把可复用步骤留在仓库脚本和文档中；避免每次聊天重新写临时部署代码。需要统一管理多个仓库/服务器时再评估相关连接器，不为单项目引入常驻MCP和额外凭据。

## 授权规则

- 改代码、检查与本地提交：按任务授权完成。
- git push、推送标签、删除远程引用：需要本次明确推送/远程修改授权。
- 上传发布包、运行生产迁移、切换或重启线上服务：需要本次明确部署授权。
- “推送”只授权推送；“部署”按指定版本部署；“推送并部署”同时授权两项。
- 旧对话中“自动推送”的约定已被2026-11-07的新要求替代。

这是仓库中的协作指令，不是Codex应用的原生权限弹窗，也不能约束任意终端程序。需要独立于agent的强制闸门时，可另配置GitHub受保护分支及带审批的生产Environment；那需要调整GitHub权限和发布方式，不能仅靠安装MCP替代。
