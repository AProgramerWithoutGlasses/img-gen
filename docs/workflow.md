## 开始一次任务

1. 运行 `npm run status`，查看本地分支、领先/落后记录、未提交文件、依赖与原稿存在情况。不要覆盖用户已有修改。
2. 需要从远端同步或准备推送时，运行 `npm run status:remote`。它限时读取远端 `main`，不 fetch、不改引用、不推送；领先/落后数量仍来自本地跟踪记录。需要刷新时再 `git fetch --prune origin`，有分歧先比较，不强推或重置。
3. 按 [文档导航](README.md) 只读相关现行说明；设计改动另核对已打开文档和未保存状态。
4. 首次安装执行根目录与 `frontend/` 的 `npm ci`；之后仅相应依赖变化或安装不完整时重装。状态命令只检查依赖入口存在，不保证锁文件一致。

状态命令不调用生产服务、不读 `.env` 正文、不安装依赖，也不检查桌面未保存画布。`npm run status -- --json` 可输出结构化本地状态，方便后续工具复用。

### GitHub 连接复现与处理

2026-11-07 复现：Git默认连接及强制HTTP/1.1均超时，显式走本机代理约1秒读取远端成功。已在本机此仓库的 `.git/config` 配置仅对GitHub生效的代理，未改全局Git、系统网络、远程URL或SSL校验：

```powershell
git config --local 'http.https://github.com/.proxy' 'http://127.0.0.1:7890'

```

本机需运行现有代理程序并监听7890；迁移电脑或更换端口后按实际地址调整，不把该本机配置提交到Git。改前配置已备份在 `outputs/network/`。恢复默认连接可执行 `git config --local --unset-all 'http.https://github.com/.proxy'`，或者取回备份中的原值；不要为解决连接问题关闭证书校验。

状态命令的远端查询有12秒上限，失败会返回非零退出码和原因类别，不自动重试、不把缓存当作已联网。读取成功只证明远端读取链路，不代表已经验证推送权限。

## 按改动选择检查

按一批累计改动安排检查，而不是每结束一次对话就全量重跑。修改过程中只做必要局部检查，工作批次完成后按下表执行受影响的检查；如果上一轮已覆盖相同输入，直接复用结果。后续小改只补受影响部分，不重新验证无关功能。

| 改动 | 需要的检查 | 不需要重复做 |
| --- | --- | --- |
| 仅文档 | `npm run check:docs`，检查描述与实际命令一致 | Go 测试、前端构建、浏览器和设计导出 |
| 根工具脚本、状态查询 | `npm run check:tools`；变更涉及的真实命令执行一次 | 无关页面和收费上游探测 |
| 前端业务 | `npm run check`、`npm run build` 及相关局部浏览器验证；需要完整模拟流程时用 `npm run verify` | 不同时再跑一遍 `verify` 中已有的类型/构建步骤 |
| 后端业务 | 先确保嵌入前端可用，再运行 `go test ./...`、`go vet ./...`、`go build ./...` | 已验证且输入未变的前端不必重装依赖/重建 |
| 前后端联动或 CI 流程 | `npm run verify:all`；需要真实 MySQL/浏览器时按下文启用 | 不再另跑 `build:server`，其中已构建并同步一次 |
| FigCraft 稿件 | 保存后 `npm run design:verify`，查看相关画面 | 普通代码改动不跑整套设计检查 |
| 设计连接/自动化工具 | `npm run design:smoke`，加相关命令验证 | 不因业务小改反复测试设计连接 |

`npm run verify` 保留 7 条模拟浏览器流程；`verify:all` 先执行工具检查，再一次前端构建与模拟流程、同步嵌入资源，最后执行 Go test/vet/build。它不自动启动 MySQL，也不会调用收费上游。

真实数据库联调仅使用**空的、专用且名称以 `_test` 结尾**的数据库。显式设置 `TEST_MYSQL_DSN`；需要真实 Go/CSP 浏览器联调时再设置 `STUDIO_BROWSER_CHECK=1`。未提供测试数据库时，相关 Go 集成测试会跳过，不能宣称已完成真实 MySQL 验证。详见 [适配验证](studio-integration.md#验证)。

复用依据是相关源码、配置与依赖输入一致。未提交的工作区也可能已经改变，不能只看Git提交号判断结果仍有效。用户明确人工验收时不重跑全量浏览器检查；验证说明列明实际运行的范围及未验证部分。

## CI 的自动步骤

`.github/workflows/ci.yml` 统一执行工具、前端 7 条模拟流程及真实 Go/MySQL 浏览器联调。一次工作流只安装一次前端依赖、构建一次前端；同一分支或 PR 的新运行取消未完成旧运行。纯 Markdown、`docs/`、`design/` 和 `archive/` 的改动不启动这套业务 CI。

CI 保留独立空测试库、race、vet、构建、真实 CSP 浏览器检查和截图。根设计工具不参与普通业务 CI，不为提速删除原有业务场景。纯文档仍由本地 `check:docs` 检查。工作流本身的变更在下一次获准推送后才会由 GitHub 实际执行。

## 提交和本地发布准备

小改可跨对话累计在工作区。完成修改和必要检查后只报告累计改动与检查结果，等待用户发话提交，不因本轮结束自动执行commit或amend，也不在每次小改后追问提交、推送或部署。

用户明确要求“提交这批改动”时，核对本批范围后统一创建本地提交；不把用户其他未授权修改带入。推送和部署仍分别等待本次授权。只要求推送时推送已有提交，不顺带创建新提交。

需要发布包时，从干净提交运行 `npm run release:prepare`：

1. 依赖锁文件、工具版本和安装记录未变化时复用依赖。
2. 前端输入及产物校验和一致时复用 `frontend/dist/` 和 `web/studio/`。
3. 同一提交、Go 版本、前端输入和二进制校验和一致时复用 Linux amd64 发布包。
4. 在 `outputs/releases/<提交号>/` 记录产物和校验和，缓存放在 `.local/release-cache/`。

该脚本只做本地准备，不运行 git push、SSH、上传或线上重启，也不替代业务测试。如果待发布改动仍未提交，先说明缺少提交授权，不能为了满足干净工作区要求而自动commit、stash或reset。文档整理通常不需要部署。发布包和缓存有变化时仅重建受影响步骤。

生产部署遵循 [DEPLOYMENT.md](DEPLOYMENT.md)：复用产物，保留队列检查、数据库/配置备份、校验和、原子切换、失败回滚及健康检查；不下载生产业务数据到本地。当前已有 Git、Node、Go、OpenSSH；无需为单项目额外引入常驻 MCP 来替代这些命令。

## 授权边界

| 动作 | 授权 |
| --- | --- |
| 本地修改、必要验证、状态查询 | 按本次任务执行 |
| 创建或修改本地提交 | 用户对本批改动明确要求提交；修改/检查/推送/部署请求不自动包含此授权 |
| 本地发布包准备 | 按任务执行；待发布版本须已有提交，不能自动提交或隐藏未提交改动 |
| 推送、推送标签、删除远端引用 | 本次明确推送或远端修改授权 |
| 上传发布包、生产迁移、切换或重启线上服务 | 本次明确部署授权 |

本地提交、推送、部署是三项独立授权。“推送”不包括部署；“推送并部署”才同时包括这两项，均不补足未获准的本地提交授权。既往授权不延续，没有默认自动提交、推送或部署。这里是协作约定，不是终端程序的权限闸门。
