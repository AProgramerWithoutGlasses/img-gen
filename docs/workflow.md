# 两人协作与设计交付

## 日常协作

每人使用自己的 img-gen 检出，以 Local 模式工作；不共用一个可写目录切换分支。main 是共同基线，大任务使用 codex/ 前缀短期分支；合并前比较远端，避免覆盖另一人的工作。小改先完成本地修改与受影响验证，再统一提交；大任务按可验证批次提交。提交、推送、发布由 agent 按 [共同规则](../AGENTS.md) 判断，文档变化无需生产部署。

开工用 `npm run status`；需要联网确认时用 `npm run status:remote`，它只读取远端，不 fetch，领先/落后仍来自本地跟踪记录。同步前再 `git fetch --prune origin`，出现分歧先比较，不强推或重置。网络配置因机器不同，不能将某人的代理端口写成全员要求。

## GitHub MCP 与本地开发

GitHub MCP 按需读取本项目的文件、提交、Issue、PR 和 Actions 状态或日志，也可检索公开项目辅助调研。使用前确认当前账号、目标仓库可见性与实际读取结果；连接失败时说明原因，改用现有 Git、网页或 API，不能用缓存冒充成功。

MCP 只读不影响本地编辑、Git 提交推送和 SSH 部署。同步仍以 fetch 后的实际引用为准，发布仍按 [部署流程](DEPLOYMENT.md) 检查。个人 MCP 安装、授权、工具清单和连通性笔记放仓库外；全局配置与令牌由各协作者在本机维护，不随本项目同步。

## 资料归属

先判断资料是否值得让另一位协作者拉取、阅读和维护，再决定保存位置。简短咨询直接在聊天里回答，不默认生成报告；需要长期保存时按用途处理：

| 内容 | 保存位置 | 提交规则 |
| --- | --- | --- |
| 个人工具、MCP、技能、操作习惯和无关项目的调研 | 仓库外的个人笔记 | 不进入项目提交或推送 |
| 临时截图、日志、执行过程与本地证据 | outputs/ | 不提交；唯一备份不能当缓存删除 |
| 对本网站有共享价值的设计或技术研究 | research/ | 保留必要结论、来源和可复用材料，按任务统一提交 |
| 已采用的接口、设计、测试与部署约定 | 对应现行说明 | 更新原说明，不复制一套新规范 |

过时盘点、重复说明和已被现行文档完全替代的过程报告可删除，历史版本仍可从 Git 查阅。有独立设计依据、接口实验事实或恢复用途的历史材料通过 [历史资料索引](history/README.md) 按需读取，不作为当前待办。个人资料误入仓库时先保存到仓库外，再移除项目副本和引用；不强推改写既有提交。

## 设计到反馈

1. 先确定本次组件范围、用户指定稿、现有授权及交付阶段，核对当前现场。新风格以本次需求为准，历史研究和旧 UI 草稿提供背景；业务契约仍须保留。
2. 先用代表组件和关键状态确认方向，候选明确禁止适配；用户批准后只启用选中的组，再补齐重复样式。只有约定“先静态、确认后实现”时才按该阶段等待；常规修复继续完成，不逐文件重复确认。原稿、色板、候选、已批准组和注释分别标记，只同步明确对象。
3. 调整尺寸前先确认浏览器缩放、CSS 像素及本次增量反馈的基准，记录最终绝对坐标；同时检查几何与实际视觉、描边、裁切和层级。保存指定稿后同步局部代码与动效；临时注入样式的预览不代表功能已实现，字号／行高变化须连同自动增高和滚动处理，不扩大到其他页面。
4. 一批累计修改由一个执行者统一构建和验收，按 [测试矩阵](../tests/README.md) 选择受影响流程；提供稳定后的截图及实际设计／代码状态。反馈进入同一批最终记录，不重放历史脚本。
5. 业务版本通过本地验证、远端比较和发布条件后，按 [部署流程](DEPLOYMENT.md) 提交、推送与上线。交付简短结果和实际线上业务版本；文档收尾提交可单独前进，不因此重建业务或重启生产。

用户无需维护文件路径。agent 负责读取相关局部规则、定位代码、管理验证和交付，普通调研按 [研究规则](../research/AGENTS.md) 独立归档。

完整操作见 [设计流程](../design/README.md)。本次复盘已采用以下改进，后续其他区域也沿用流程，而非沿用当前对话框的具体样式：

| 本次耗时或返工来源 | 后续处理 |
| --- | --- |
| 未先核实浏览器缩放，连续放大再缩小 | 先建立缩放、视口与实际尺寸基线，同一画布比较原尺寸 |
| 方向未定就铺开大量重复画板 | 先做小样和关键态，确认方向后补完整状态；小修直接更新对应批准组 |
| 增量反馈套用旧版基准，或字号变化后仍按旧行高增高 | 用最近预览记录增量和最终绝对值；自动增高读取 CSS 行高，验证自然折行、滚动、清空和底边锚定 |
| 同路径多窗口误选现场，工具报错后仍继续保存 | 桌面使用已确认文档 ID 和 dirty 状态；headless 与未保存现场只同步明确属性；成功后再执行依赖步骤 |
| 父子层分别缩放，内线和圆角漂移；圆钮又被工具栏裁切 | 用外框和固定内距推导几何，光学补偿独立参数化，检查实际可见边界 |
| 多执行者重复检查、导出整稿，检查结果与当前目标不匹配 | 同一输入只有一位验收执行者；按测试矩阵补受影响检查，根工具未变时不重跑工具测试，使用当前指定稿和局部场景 |
| 安装、构建、逐文件校验或报告与业务目标脱节 | 依赖未变不重装；一次构建复用；校验和集中用于产物完整性和缓存判断，不代替视觉验收；只保存最终可接续记录 |
| 每轮保留完整旧备份及上传副本，磁盘不断增长 | 按恢复依赖保留备份与版本，清理已替代产物，发布后检查余量与临时上传文件 |

## 依赖、构建和本地发布包

首次或锁文件变化才安装相应依赖；前端输入变化后根 `npm run build` 一次同步 web/studio。相同输入通过证据可复用，输入包括未提交源码、配置与依赖，不能只依据提交号判断。

`npm run release:prepare` 从干净提交准备 Linux amd64 二进制，在 outputs/releases/ 写清单、校验和，缓存放 .local/release-cache/；它本身不推送、上传或重启。agent 先完成本批提交后再准备产物，不 stash 隐藏其他人的工作。备份、队列检查、原子切换和健康检查不能因缓存优化省略。

缓存不能命中时先查输入和工具版本的差异，不盲目重复安装或构建。已经验证过的相同前端产物可用于后续发布；如果准备工具无法复用，允许按部署说明手动准备，但必须说明复用边界。文档或清理任务不构建前后端，也不运行无关业务测试。

## 清理与保留

先盘点具体路径、大小、用途和恢复依赖，再执行已经授权的清理；按目录名称或日期判断不明的内容先保留。只删除已被保留版本替代的备份、可再生缓存、重复产物与失效临时脚本，禁止整清 outputs 或删除仍唯一的设计恢复材料。

本地保留当前设计与原始素材、最新交付证据、必要历史研究和实测；可清理已关闭的独立测试数据目录、过期构建与重复截图。依赖和有效缓存保持可用，避免清理后为了继续工作重新安装。服务器的备份和二进制保留规则见 [部署流程](DEPLOYMENT.md#备份版本与容量)。数据库、生成图片、用户上传及业务记录不属于历史备份清理范围。

删除前检查绝对路径在本次范围内、不是链接跳转、未被当前服务／设计会话使用；清单和执行结果写入忽略的 outputs，交付释放量及保留内容。用户已明确授权的例行清理无需逐项再问；遇到唯一资料或无法确认的恢复依赖，不以“太老”作为删除理由。

历史整理资料只用于追溯，不把旧聊天路径、旧网络配置和历史分支状态作为当前要求。现行目录见 [文档导航](README.md)。
