# 服务器部署与升级

站点：`https://img.xunxun.me`，通过 `ssh me` 连接 Ubuntu 服务器。

本批提交、推送与发布由 agent 按 [共同规则](../AGENTS.md) 自动判断时机；本地条件不满足时说明阻塞。实际部署仍须完成下述备份、队列、校验和与健康检查。

既有部署机器的 OpenSSH 配置示例： `~/.ssh/config` 使用 `Host me`，连接 `root@8.140.237.54`，指定 `~/.ssh/id_ed25519_aliyun_me` 和 `IdentitiesOnly yes`。专用公钥追加到服务器的授权列表，保留原有密钥；私钥仅保存在本机，不进入仓库。`ssh me` 是 SSH 主机别名，不依赖 PowerShell alias。

## 运行位置

- 应用：`img-gen.service`，以 `imggen` 用户运行，监听 `127.0.0.1:18080`。
- 当前二进制：`/opt/img-gen/current`，指向 `/opt/img-gen/releases/` 下的版本文件。
- 应用配置：`/opt/img-gen/.env`，权限 `root:imggen 0640`；保留服务器原有 API Key、Base URL 和数据库连接。
- HTTPS 会话需要 `COOKIE_SECURE=true`。首次账号迁移使用 `ADMIN_PASSWORD`，未设置时兼容原 `APP_PASSWORD`；已有账号不会被环境变量重置密码。
- MySQL：独立容器 `img-gen-mysql`，数据卷 `img-gen-mysql-data`，监听 `127.0.0.1:13306`，数据库名 `imggen`。此部署沿用既有 MySQL 8.2 容器。
- Nginx：`/etc/nginx/sites-available/img-gen`；`client_max_body_size 25m` 覆盖新版每张附件20MB的独立上传及旧双图表单上限；证书由 `certbot.timer` 续期。调整后先执行 `nginx -t`，通过后 reload。
- 升级备份：`/opt/img-gen/backups/<UTC时间>/`，目录权限 `0700`，备份文件权限 `0600`。
- 发布信息：`/opt/img-gen/release.json`，记录代码提交、二进制 SHA256、前一版本与备份位置，不保存密钥。

## 升级顺序

1. 等待同一项目其他会话完成，核对 `git status`、各分支及未推送提交；禁止将环境文件、数据库、日志或 `outputs/` 加入 Git。
2. 按累计改动范围做一次必要检查，相关源码、配置和依赖输入一致的已有结果可复用，新改动只补受影响检查；不能只凭Git提交号相同复用未提交工作区的旧结果。用户明确人工验收时不反复运行全量浏览器流程。MySQL 集成测试只能使用空的、名称以 `_test` 结尾的专用数据库。
3. 使用本批验证后创建的干净提交执行 `node scripts/prepare-release.mjs`，生成或复用Linux amd64产物和清单。待发布改动先完成本批提交，不能隐藏或丢弃其他协作者的修改。依赖未变化不重装，前端输入和产物未变化不重建，同一提交的完整产物可复用。核对远端后推送本批版本；确认部署条件满足再上传和切换。也可按原方式手动构建，但不得遗漏前端构建。
4. 上传到 `/opt/img-gen/releases/img-gen-<完整提交号>`，比较本机和服务器的 SHA256。
5. 确认没有 `queued` / `running` 任务后停止应用，备份数据库和配置。不要重试不确定是否已经计费的任务。
6. 原子切换 `current` 软链接，启动服务，等待 `/healthz` 返回成功。数据库兼容迁移由程序启动时执行。
7. 检查健康与公网首页、资源来源。相关页面可由用户手动验收，不重复全站浏览器测试；不调用收费生图或润色接口。
8. 核对远端分支、已验证提交和线上 release.json 一致；推送或发布受阻时分别报告，不把本地准备当作已上线。

纯文档收尾提交不要求生产二进制跟随变动；交付时区分线上业务提交和后续文档提交，不能为了提交号相同重新构建或重启。

同批验证中只有前端补丁、后端源码和依赖均未改变时，可复用本轮已验证且仍可恢复的完整数据库备份；记录其来源和摘要，并另存补丁切换前的配置与版本元数据。不以备份复用为由跳过队列、产物、健康或容量检查。

启动失败可将 `current` 切回前一二进制并恢复原配置。数据库迁移独立于二进制切换；恢复数据库前必须核对迁移和新增业务数据，不能自动覆盖线上数据库。

首次启用积分系统后，账号初始余额为 0、模型初始价格为每张 1 积分。管理员需在后台按实际需要配置价格和增加余额；部署过程不擅自调整业务积分。

## 备份、版本与容量

发布或已授权维护时盘点容量，不等停止应用后才发现空间不足。现行备份默认保留最近 3 个完整成功批次，加上仍有独立迁移／恢复用途的基线及用户指定长期保留项；同日重复旧快照已被这些完整备份替代时可清理。没有新式完成标记的早期 SQL 备份不等于失败，需按其实际文件和恢复用途判断。

二进制至少保留 current、直接 previous 和另一个近期可回退业务版本；还须保留上述备份直接恢复所需的旧二进制，即使它超出最近 3 个。清理清单明确标出这些依赖，不递归保留所有过时历史链，也不删除仍被 current 或现行恢复点引用的目标。

备份清理只涉及明确的历史快照和对应过期版本，不删除实时 MySQL 数据卷、生成图片、用户上传、账号、任务与积分记录。唯一资料、未知用途目录和其他项目的 Docker 数据先保留；不能以清磁盘为由泛用全盘或全 volume 清理。

操作前核对保留备份的完整性证据、当前版本和路径；用明确清单删除，记录释放量，核对服务与健康。成功发布后可以移除与正式产物逐字节一致的临时上传副本；正式版本和备份按上述策略留存。本地发布包同样按恢复用途清理，不影响线上现有文件。

磁盘预算应覆盖新产物、压缩备份和余量。可以用最近已验证的完整压缩备份估算，并给增长留余量；没有可靠基线时回退保守估算。备份写入期间设置输出上限并持续检查可用空间，保护至少 2GiB 余量，超限失败后恢复原服务；不能只调低预算常数绕过预检。若保留点都不可清理且空间仍不足，先扩容或安排归档，不冒充发布成功。

选择本地归档方式前估算备份大小和传输速率。大文件下载不应占住停服窗口：服务器容量允许时，先在受限目录写入有容量上限的临时完整备份并校验，完成程序切换和健康检查，恢复服务后再传回本地。本地归档须校验完整性、各成员摘要和gzip，再将发布元数据指向本地恢复点；确认该恢复点可用后，只移除本次明确的临时备份。空间不允许服务器临时落盘时才采用直接流向本地的方案，并按实际带宽设置停止服务的时间上限和失败恢复。

## 常用只读检查

```sh
systemctl is-active img-gen nginx certbot.timer
readlink -f /opt/img-gen/current
cat /opt/img-gen/release.json
docker inspect --format '{{.State.Health.Status}}' img-gen-mysql
curl -fsS http://127.0.0.1:18080/healthz
nginx -t
df -h /
```

部署证据、浏览器截图和本地操作脚本放在被 Git 忽略的 `outputs/` 中。不得在维护说明或 Git 提交中保存账号密码、API Key、数据库备份或完整上游响应。
